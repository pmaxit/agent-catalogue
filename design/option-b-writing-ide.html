Consistency Models

Distributed systems force a trade: either every client sees the same world at the same instant, or the system stays available when the network does not. Consistency models name the promises you can still make when physics gets in the way.

Linearizability

Linearizability is the strongest practical guarantee. Each operation appears to take effect at a single point between its invocation and response, and that order matches real time. Clients never observe stale reads relative to a completed write — even across replicas.

When it is wrong Cross-region user-facing reads under partition. Holding the line for linearizability means refusing availability; most consumer products cannot pay that cost.

Sequential consistency

Operations from all clients appear in a single total order that respects each client's program order — but that order need not respect real-time. A write may become visible later than a wall-clock clock would suggest, as long as every client agrees on the sequence.

Causal consistency

Only causally related operations must be ordered. Concurrent writes may diverge and reconcile later. This is the sweet spot for collaborative editors and social timelines: you preserve "happened-before" without global agreement.

// Read-repair sketch
onRead(key):
  vals ← quorumGet(key)
  if diverge(vals):
    winner ← reconcile(vals)
    asyncRepair(replicas, winner)
  return winner
