Chapter 3 — Consensus & Commit: Ownership, Not Voting

Quarto draft • 1,742 words • judging 0.79 • Loop 2

Most textbooks start with voting. That metaphor hides the actual invariant: consensus is a mechanism for assigning exclusive ownership over positions in a shared log, with fencing that prevents stale owners from corrupting history. Get that wrong and you get systems that “agree” but still lose writes.

Invariant — single owner per log position. At any time, at most one proposer can consider itself owner of position n. Ownership is granted by a quorum of acceptors and revoked only by a higher proposal number. This is what prepare/promise enforces.

1. Prepare / Promise as ownership claim

Think of prepare(n) as: “I am attempting to become owner of all unowned positions ≥ n”. An acceptor promises not to accept anything < n and returns the highest accepted value it has. This is not a vote — it is a fence.

python — paxos.py⌘C Run
def prepare(proposal_id, quorum): promises = [] for acc in quorum: p = acc.on_prepare(proposal_id) # returns (ok, highest_accepted) if not p.ok: return None promises.append(p) # owner candidate: pick highest accepted value or own value chosen = max(promises, key=lambda x: x.accepted_id).value or own_value return chosen # trace N=3, prop 5 → promise(1,None), promise(2,None), promise(3,v=2) → picks v=2

2. Why 2PC is not consensus

Two-phase commit blocks on coordinator failure because it optimizes for atomicity with a single decision maker, not for progress under partition. Paxos guarantees that some value will eventually be chosen if a majority lives, even if previous owners die mid-protocol. The table makes it explicit:

3. Three liveness pitfalls you will actually hit

1) Dueling proposers. Without leader election, proposal numbers chase each other and no value stabilizes. Fix: stable leader lease.

2) Unbounded prepare storm after partition heal. Every node retries prepare(n++) — acceptors do O(n) work. Fix: exponential backoff + prepare coalescing.

3) Log hole on owner crash before accept. Quorum saw promise but not accept; next owner must discover nothing chosen and propose no-op. Fix: explicit no-op filler on leader change.

Takeaway — implement fencing, not voting. If your system cannot show, for every write path, which fencing token was checked and what happens if the check fails, you don't have consensus — you have hope.
